# Agent Pipeline — инструкции для агента

Этот файл читают агенты, работающие по конвенции `AGENTS.md`: Codex, Cursor, Jules, Aider и
другие. В Claude Code те же процедуры доступны как скиллы и слэш-команды `/pipeline:init`,
`/pipeline:ship`, `/pipeline:fix-ci` — содержание одинаковое, отличается только способ вызова.

Система устроена так, что от агента зависит только удобство, а не работоспособность:
`.pipeline/config.yml`, сгенерированные workflow и `scripts/pipeline.sh` работают в CI и на
машине разработчика без всякого ИИ.

## Как вызывать инструмент

Ниже `PIPELINE` — команда запуска генератора. Возьмите первый доступный вариант:

    npx --yes github:DEMest/agent-pipeline            # ничего ставить не нужно
    node /путь/к/клону/agent-pipeline/src/cli.mjs     # если репозиторий уже склонирован
    node "${CLAUDE_PLUGIN_ROOT}/src/cli.mjs"          # внутри Claude Code

Проверить, что вызов работает, можно запуском без аргументов: он печатает подсказку по
использованию и завершается ненулевым кодом.

Команды инструмента:

    $PIPELINE generate <каталог проекта>       создать или обновить артефакты из конфига
    $PIPELINE check <каталог проекта>          проверить, что артефакты не разошлись с конфигом
    $PIPELINE diagnose <каталог> <файл лога>   разобрать лог упавшего прогона CI
    $PIPELINE upgrade <каталог проекта>        пересобрать артефакты новой версией инструмента

## Процедура 1. Развернуть пайплайн в проекте

Считается выполненной не когда файлы записаны, а когда CI на pull request зелёный. Записать
конфиг с выдуманными командами и уйти — основной способ провалить эту процедуру.

**Сначала проверить окружение**, до всякой генерации:

1. `gh auth status` — у токена должен быть scope `workflow`, иначе пуш `.github/workflows/`
   отклоняется, хотя всё остальное работает. Чинится `gh auth refresh -h github.com -s workflow`.
2. `gh api repos/<owner>/<repo>/actions/permissions --jq '.enabled'` — если `false`, pull request
   будет ждать проверок, которых никто не запустит. Включать только с согласия человека.
3. Удалённого репозитория нет — предложить `gh repo create`, спросив про приватность.

**Определить самостоятельно, не спрашивая человека:** стек по файлам (`package.json`,
`pyproject.toml`, `go.mod`, `pom.xml`, `build.gradle`); реальные команды проверок из самого
проекта, а не из головы; состояние репозитория через `gh repo view`. Прогнать найденные команды
и посмотреть, что происходит — команда, которой в проекте нет, сделает CI красным сразу.

Стек-специфичные детали — в `skills/pipeline-init/SKILL.md`, разделы «Если стек …». Там же
описано, что делать с пустой папкой: стек тогда не определяется, а выбирается в разговоре, и
обязательно ставятся зависимости, чтобы появился файл блокировки (без него `npm ci` в CI падает).

**Спросить у человека** только то, чего нет в файлах: цель проекта, режим автономности
(`full`, `merge-gate`, `prod-gate`), адрес сервера и registry, что считается продом.

**Сгенерировать и доказать:**

    $PIPELINE generate .
    sh scripts/pipeline.sh all

Затем ветка, коммит, `gh pr create`, `gh pr checks --watch` — и не останавливаться, пока
проверки не зелёные.

## Процедура 2. Провести задачу до мерджа

1. Прочитать `.pipeline/config.yml`: что запускать (`checks`), что обязательно (`required`),
   кто принимает решение о мердже (`autonomy`), на какой стадии проект (`stage`).
   Если файла нет — пайплайн не настроен, начните с процедуры 1.
2. Убедиться, что локальная `main` совпадает с удалённой: `git fetch` и сравнить
   `git rev-list --left-right --count main...origin/main`. Расхождение здесь означает, что
   ветка отпочкуется не от того состояния, которое увидит CI.
3. Создать ветку `feat/<короткое-имя>` от актуальной `main`.
4. Со стадии `shaping` сначала пишется тест на желаемое поведение, и он должен покраснеть до
   появления реализации. Тест, который ни разу не падал, ничего не доказывает.
5. Прогнать проверки локально до зелёного: `sh scripts/pipeline.sh all`. Каждый круг
   «запушил — подождал CI — получил красное» стоит минут, локальный прогон — секунд.
6. Если менялся `.pipeline/config.yml`, перегенерировать артефакты (`$PIPELINE generate .`),
   иначе джоба `drift-check` покраснеет.
7. Зафиксировать изменения коммитом, запушить ветку, открыть pull request. В теле — что
   сделано и какими командами проверено, а не пересказ диффа.
8. `gh pr checks --watch`. Красный CI — процедура 3, не чинить вслепую.
9. Мердж по режиму из конфига: `full` — мерджить самому; `merge-gate` — остановиться и сообщить
   человеку, что PR зелёный и ждёт его; `prod-gate` — смерджить и не запускать выкатку.

## Процедура 3. Починить красный CI

Задача — понять, что сломалось, и починить причину. Ослабить проверку, отключить тест или
подвинуть порог, чтобы «прошло», — это не починка, а сокрытие.

**Сначала посчитать попытки, до всякой работы.** Лимит — три на один pull request, и он не
хранится в памяти сессии: сессия могла прерваться. Источник правды — комментарии к PR:

    gh pr view --json number,comments --jq '.comments[].body' | grep -o 'Попытка [0-9]*'

Наибольшее найденное число — сколько попыток уже сделано. Три — остановиться и отчитаться
человеку, не начиная чинить.

**Взять диагноз, а не сырой лог:**

    gh run list --limit 10 --json databaseId,conclusion,headBranch
    gh run view <id> --log-failed > /tmp/failed.log
    $PIPELINE diagnose . /tmp/failed.log

Диагноз называет упавшую джобу, шаг, сообщения об ошибках и — если шаг соответствует проверке
из конфига — её команду и обязательность.

**Различать два случая.** Красная `drift-check` означает, что конфиг поменяли, а артефакты не
перегенерировали: лечится `$PIPELINE generate .` и коммитом результата. Красная `checks`
означает упавшую проверку проекта: воспроизвести её локально той же командой, прежде чем
что-то править. Правка вслепую по тексту ошибки из CI — самый частый способ потратить попытку.

**После каждой попытки** оставить комментарий, чтобы счётчик пережил перезапуск сессии:

    gh pr comment <номер> --body "Попытка N: <что было сломано> → <что изменено> → <результат>"

## Процедура 4. Обновить пайплайн под новую версию инструмента

Артефакты лежат в репозитории проекта, а инструмент развивается отдельно. Проект,
развёрнутый полгода назад, продолжает жить со старым workflow, и `drift-check` этого
не замечает: он сверяет артефакты с конфигом, а расходится не конфиг, а генератор.

    $PIPELINE upgrade .

Команда пересобирает артефакты и печатает, какие из них изменились и какой версией были
собраны раньше. Если ничего не изменилось, она так и говорит и файлы не трогает.

Изменения нужно просмотреть через `git diff` и провести обычным путём — через ветку и
pull request, как любую другую правку. Это не формальность: обновление меняет то, что
проверяет и выкатывает CI, и заслуживает такого же зелёного прогона, как изменение кода.

## Чего не делать

- Не объявлять работу законченной, не дождавшись зелёного CI: зелёные локальные проверки при
  красном или неизвестном CI — не результат.
- Не редактировать сгенерированные файлы руками: `ci.yml`, `deploy.yml`, `scripts/pipeline.sh`
  перезаписываются при следующей генерации. Менять надо `.pipeline/config.yml`.
- Не убирать проверку из `required` и не ослаблять её ради прохождения PR.
- Не пушить с `--force` в ветку pull request.
- Не хранить значения секретов в `.pipeline/config.yml`: он коммитится, там только имена.
