# Развёртывание пайплайна в проекте

Init считается завершённым не когда файлы записаны, а когда CI на PR зелёный.
Записать конфиг с выдуманными командами и уйти — основной режим отказа этого скилла.

## Шаг 1. Проверка окружения (до генерации)

Три отказа, которые иначе проявятся в середине процесса. Первые два проверяются прямо сейчас,
до всякой генерации, — для них не нужно ничего, кроме доступа к репозиторию. Третья, атрибуция
коммитов, ждёт первого коммита: раньше проверять нечего. Поэтому она вынесена в Шаг 5 и делается
там в два приёма — локально до `git push` и через API после него.

1. `gh auth status` — токен должен иметь scope `workflow`. Без него пуш `.github/workflows/`
   отклоняется, хотя всё остальное работает. Если scope нет —
   `gh auth refresh -h github.com -s workflow`.
2. Включены ли Actions в репозитории:
   `gh api repos/<owner>/<repo>/actions/permissions --jq '.enabled'`. Если пришло `false` — PR
   будет ждать проверок, которых никто не запустит. Сообщить об этом человеку и предложить
   включить (`gh api repos/<owner>/<repo>/actions/permissions -X PUT -f enabled=true` либо вручную
   в Settings → Actions → General) — включать только с явного согласия человека, это настройка
   репозитория.
3. Атрибуция коммитов — проверяется в Шаге 5: локально до пуша и через API после него.

Если удалённого репозитория нет — предложить `gh repo create`, спросив про приватность.
Создавать только с явного согласия человека.

## Шаг 2. Расследование

Определить самостоятельно, не спрашивая:

- стек — по `package.json` / `pyproject.toml` / `go.mod` / `pom.xml` / `build.gradle`;
- реальные команды — из раздела `scripts` в `package.json`. Не подставлять команду из пресета,
  если её нет в проекте: пресет `templates/stacks/node-ts/preset.json` даёт кандидатов, но
  попадают в конфиг только те, что действительно существуют;

- имена `all` и `esac` в конфиг не переносить как есть — валидатор их отклоняет (`all` совпадает
  с агрегатной командой сгенерированного скрипта, `esac` закрывает конструкцию `case` и ломает её
  разбор). Если в `package.json` есть скрипт с таким именем, при переносе в конфиг переименовать
  (например, `all` → `check_all`), а саму команду оставить прежней;
- состояние репозитория — `gh repo view`;
- работоспособность проверок — прогнать их и посмотреть, что происходит.

### Если стек java

Система сборки определяется по файлам и записывается в конфиг полем `project.build`:
`pom.xml` — значит `maven`, `build.gradle` или `build.gradle.kts` — значит `gradle`. Угадать её
позже по командам нельзя, а от неё зависят и команды, и кэш в CI, и место сборочного артефакта.

Пресет команд берётся соответствующий: `templates/stacks/java/preset-maven.json` либо
`preset-gradle.json`. Команды идут через обёртку проекта (`./mvnw`, `./gradlew`), а не через
системные `mvn` и `gradle`: обёртка фиксирует версию сборщика, и на машине разработчика и в CI
собирается одинаково.

Версию JDK взять из проекта, а не из головы: у Maven это свойство `java.version` или
`maven.compiler.release` в `pom.xml`, у Gradle — блок `java { toolchain { languageVersion } }`
либо `sourceCompatibility`. Записать её в `project.java_version`. Если версия в проекте не
указана, оставить поле пустым — тогда CI возьмёт 21.

Если в конфиге есть секция `deploy`, копировать `templates/stacks/java/Dockerfile.maven` или
`Dockerfile.gradle` по системе сборки. Шаблон под Gradle собирает `bootJar` — это команда плагина
Spring Boot; в проекте без него сборочную строку нужно поменять и сказать об этом человеку.
### Если стек python

Менеджер зависимостей определяется по файлам и записывается в `project.build`:
`poetry.lock` или секция `[tool.poetry]` в `pyproject.toml` — значит `poetry`;
`uv.lock` — значит `uv`; иначе `pip`. От этого зависят и команды проверок, и то,
что кэшируется в CI.

Пресет берётся соответствующий: `templates/stacks/python/preset-pip.json`,
`preset-poetry.json` или `preset-uv.json`. В конфиг попадают только те команды,
которые в проекте действительно работают: если `ruff` или `mypy` не установлены
и не объявлены в зависимостях, проверку не добавлять — она сразу сделает CI красным.

Версию интерпретатора взять из проекта: `requires-python` в `pyproject.toml`,
`python_requires` в `setup.cfg` либо файл `.python-version`. Записать в
`project.python_version` в виде `3.12` — только minor, без патч-версии.

Если есть секция `deploy`, скопировать `Dockerfile.pip`, `Dockerfile.poetry` или
`Dockerfile.uv` из `templates/stacks/python/`. Во всех трёх строка `CMD` написана
под uvicorn и почти наверняка не подходит проекту — поправить под его фреймворк
и точку входа, а не оставлять образ, который не поднимется при первой выкатке.

### Если стек go

Поле `project.build` для go не нужно и валидатором отвергается: модули и кэш
встроены в сам инструмент, выбирать нечего.

Пресет — `templates/stacks/go/preset.json`. Версию взять из директивы `go` в
`go.mod` и записать в `project.go_version`; если хочется всегда свежую, оставить
поле пустым — тогда CI возьмёт `stable`.

Шаблон `templates/stacks/go/Dockerfile` собирает пакет из корня репозитория
(`go build ... .`). Если `main` лежит в `cmd/<имя>`, поправить путь сборки —
иначе образ соберётся пустым или сборка упадёт.

### Если в папке пусто

Расследование в пустой папке ничего не находит, и это нормальный сценарий: человек начинает
проект с нуля. Стек тогда не определяется, а выбирается — спросить в интервью, чем он будет
писать, и не угадывать.

Дальше создать минимальный скелет, чтобы пайплайну было что проверять. Для `node-ts` это
`package.json` со скриптом `test`, каталог `tests/` и `templates/stacks/node-ts/smoke.test.mjs`
в нём. Для `java` — скелет проще получить у Spring Initializr (`https://start.spring.io`), чем
собирать вручную, и там же сразу выбирается система сборки.

**Обязательно выполнить установку зависимостей и закоммитить файл блокировки.** Для `node-ts`
это `npm install`, создающий `package-lock.json`. Сгенерированный CI ставит зависимости командой
`npm ci`, а она без файла блокировки падает — новый проект получил бы красный CI на первом же
прогоне, ровно там, где пайплайн должен доказывать свою работоспособность. То же для java:
обёртка `./mvnw` или `./gradlew` должна быть в репозитории.

Стадия у нового проекта — `sketch`: на ней тесты ещё не обязательны, и smoke-теста достаточно,
чтобы CI был зелёным до появления первой фичи.

Если каталог ещё и не репозиторий git — выполнить `git init`, прежде чем говорить о PR.

## Шаг 3. Интервью

Спросить только то, что нельзя узнать из файлов: цель проекта, режим автономности
(`full` / `merge-gate` / `prod-gate`), хост и registry, что считается продом.

Для пустой папки к этому добавляется выбор стека — определить его по файлам нельзя, потому что
файлов нет.

## Шаг 4. Генерация

Источники плейсхолдеров шаблона:

- `{{NAME}}` — поле `name` из `package.json` проекта; если его нет — имя каталога проекта.
- `{{STACK}}` — определён в Шаге 2.
- `{{GOAL}}` — получен в Шаге 3.
- `{{AUTONOMY}}` — получен в Шаге 3.
- `{{STAGE}}` — для нового проекта всегда `sketch`.

Заполнить `templates/common/config.yml.tmpl`, записать в `.pipeline/config.yml`, затем перед вызовом
генератора проверить, установлена ли его зависимость, и поставить при отсутствии:

    test -d "${CLAUDE_PLUGIN_ROOT}/node_modules/yaml" || npm install --omit=dev --prefix "${CLAUDE_PLUGIN_ROOT}"

Плагин попадает на диск клонированием репозитория, а `node_modules/` в `.gitignore` — зависимости
с ним не приезжают. Без этой установки первый же вызов генератора падает с
`ERR_MODULE_NOT_FOUND: Cannot find package 'yaml'`. Установка нужна один раз: при повторных запусках
`node_modules/yaml` уже на месте, и команда ничего не делает. `${CLAUDE_PLUGIN_ROOT}` — переменная,
которую Claude Code сам подставляет плагинам; путь плагина не нужно угадывать.

    node "${CLAUDE_PLUGIN_ROOT}/src/cli.mjs" generate .

Для пустого проекта скопировать `templates/stacks/node-ts/smoke.test.mjs`, чтобы CI был зелёным
до появления первой фичи.

Если в конфиге есть секция `deploy`, скопировать в проект два файла:

- `templates/deploy/docker-vps/compose.yml` → `deploy/compose.yml`. Без него выкатка упадёт на
  шаге копирования на сервер: workflow берёт файл именно оттуда;
- `templates/stacks/node-ts/Dockerfile` → `Dockerfile` в корне, но только если своего нет.
  Workflow собирает образ командой `docker build .`, то есть из корня проекта. Чужой Dockerfile
  не трогать: он почти наверняка точнее шаблонного.

Шаблонный Dockerfile копирует в финальный образ каталог `dist`. Если проект собирается иначе или
не собирается вовсе, поправить эту строку под проект — и сказать об этом человеку, а не оставить
образ, который не соберётся при первой же выкатке. Заодно сказать человеку, что выкатка не заработает, пока он
сам не сделает три вещи, недоступные агенту:

1. заведёт в репозитории секреты `SSH_KEY` и `REGISTRY_TOKEN`;
2. назначит проверяющих у GitHub Environment для окружения с `auto: false` — иначе одобрение
   не запросится и выкатка на прод пройдёт молча;
3. проверит, что на сервере стоит Docker и есть пользователь из поля `host`.

Настройки проекта: основной сценарий из README — существующий проект, где `.claude/settings.json`
уже может быть, со своими хуками и правами, которые нельзя терять слепым копированием шаблона
поверх.

- Если файла `.claude/settings.json` в проекте нет — скопировать `templates/common/claude-settings.json`
  как есть.
- Если файл уже существует — не перезаписывать его. Прочитать существующий JSON, добавить в его
  `hooks.SessionStart` запись из шаблона (создав секцию `hooks.SessionStart`, если её не было),
  сохранив остальные хуки, права и прочие настройки проекта нетронутыми.

В обоих случаях показать человеку, что именно изменилось в `.claude/settings.json` — новый файл
целиком либо только добавленную запись, — прежде чем продолжать.

Скопировать `templates/common/hooks/pipeline-status.sh` в `.claude/hooks/`, чтобы следующий человек,
открывший проект, увидел состояние пайплайна без единой команды.

## Шаг 5. Доказательство

    sh scripts/pipeline.sh all

Затем ветка и первый коммит.

Атрибуция коммитов проверяется в два приёма, потому что одной командой это не делается.

**До `git push`** — локально, потому что удалённый репозиторий ещё не знает о коммите:

    git log -1 --format='%ae'
    gh api user --jq '"\(.id)+\(.login)@users.noreply.github.com"'

Адреса должны совпадать. Не совпали — выполнить `git config --local user.email` с адресом из
второй команды и переписать уже сделанный коммит: `git commit --amend --reset-author --no-edit`.
Делается до пуша, пока коммит не уехал в `origin` с чужим авторством.

**После `git push`** — подтверждение фактической атрибуции на стороне GitHub:

    gh api repos/<owner>/<repo>/commits --jq '.[0].author.login'

Пусто или чужой аккаунт — значит адрес не привязан к аккаунту: проверить настройки почты в
профиле GitHub. Именно эта команда, а не локальная, показывает, кому GitHub припишет коммит.

Обе проверки нужны: локальная предотвращает, удалённая подтверждает. Ни одну нельзя было
выполнить в Шаге 1 — там ещё нет коммита.

Затем `git push`, `gh pr create`, и `gh pr checks --watch`.
Скилл завершён только когда проверки зелёные. Красные — чинить, а не отчитываться об успехе.
