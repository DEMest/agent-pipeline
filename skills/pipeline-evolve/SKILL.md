# Взросление проекта

Набросок из трёх файлов и сервис с пользователями требуют разной строгости. Стадия живёт
в `.pipeline/config.yml` полем `stage` и меняется не по ощущению, а по наблюдаемым метрикам.

## Шаг 1. Посмотреть, вырос ли проект

    node "${CLAUDE_PLUGIN_ROOT}/src/cli.mjs" state .

Команда печатает метрики и говорит, перерос ли проект текущую стадию, перечисляя основания
с числами. Снимок пишется в `.pipeline/state.json` только когда вывод изменился — иначе
каждый прогон создавал бы диф, и настоящий переход утонул бы в шуме.

Не перерос — сказать об этом прямо и остановиться. Придумывать взросление, которого метрики
не показывают, значит навязывать проекту строгость, к которой он не пришёл.

## Шаг 2. Отдельный PR, не попутно с задачей

Переход меняет правила, по которым проверяется весь код проекта. Смешать его с фичей значит
спрятать смену правил внутри чужого диффа, где её никто не обсудит.

Ветка называется по смыслу перехода, например `chore/stage-product`.

## Шаг 3. Что именно ужесточать

- `sketch` → `shaping`: тесты в `required`; линт добавляется, но пока не валит сборку
  (в конфиг он попадает вне `required`);
- `shaping` → `product`: линт переходит в `required`, добавляются проверка типов и аудит
  зависимостей (`npm audit`, `pip-audit`, `govulncheck`, `mvn dependency-check` — по стеку);
  если есть миграции, включается `backup_before_migrate` в секции `deploy`;
- `product` → `sustained`: порог покрытия, матрица версий рантайма, сканирование безопасности.

Добавлять только те проверки, которые в проекте реально запускаются. Проверка, которой нет
в зависимостях, сделает CI красным на первом же прогоне — это не ужесточение, а поломка.

## Шаг 4. Храповик: не ломать написанное

Главная причина, по которой ужесточение проваливается: включили строгое правило, получили
сотни ошибок в старом коде, выключили правило целиком. Строгость после этого не растёт,
а исчезает вместе с доверием к инструменту.

Поэтому новые правила применяются к изменённому коду, а не ко всей истории:

- линт — по списку из `git diff --name-only origin/main...HEAD`;
- проверка типов — по тому же списку либо с baseline-файлом, фиксирующим текущие ошибки;
- покрытие — порог «не ниже текущего значения», а не абстрактные 80%;
- для go — `golangci-lint run --new-from-rev=origin/main`, это встроено в сам инструмент.

Зафиксированное состояние старого кода хранится в `.pipeline/baseline.json` и может только
уменьшаться: правило, однажды применённое к файлу, обратно не отключается.

## Шаг 5. Довести до зелёного

После правки конфига перегенерировать артефакты, иначе `drift-check` покраснеет:

    node "${CLAUDE_PLUGIN_ROOT}/src/cli.mjs" generate .

Затем обычный путь: коммит, PR, `gh pr checks --watch`. В теле PR — что изменилось в правилах
и почему проект считается выросшим (основания из шага 1, с числами).

Красный CI на этом PR — важный сигнал: значит ужесточение задело существующий код, и надо
не ослаблять правило обратно, а сузить его до изменённых файлов по шагу 4.

## Сигналы боли

Не всё выводится из файлов. Откат прода, второй баг в том же месте, main, простоявший красным
сутки, — это данные о том, что текущих проверок уже не хватило. Записывать их в
`.pipeline/state.json`, поле `painSignals`, строкой с датой:

    "painSignals": ["2026-08-30 откат прода: healthcheck не прошёл после миграции"]

Каждый такой сигнал поднимает стадию на ступень независимо от размера проекта. Довод
«проверок не хватило» весомее любого счётчика строк.
