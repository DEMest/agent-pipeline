# Проведение задачи от промпта до мерджа

Скилл ведёт задачу через одинаковый путь: ветка → изменение → локальные проверки → PR →
зелёный CI → мердж по режиму, записанному в проекте. Он не описывает, как программировать —
для этого есть навык разработки через тесты; он описывает дисциплину вокруг кода.

## Шаг 1. Прочитать состояние проекта

`.pipeline/config.yml` — что запускать (`checks`), что обязательно (`required`), кто принимает
решение о мердже (`autonomy`), на какой стадии проект (`stage`).

`.pipeline/conventions.md`, если он есть, — принятые в проекте решения. Прочитать целиком
перед работой и соблюдать: файл существует именно затем, чтобы задача, сделанная сегодня, не
противоречила решению, принятому месяц назад.

**Принятое по ходу работы решение дописывать туда же, одной строкой с датой и причиной.**
Записывается выбор между равноценными вариантами — то, что нельзя вывести из кода: почему эта
библиотека, а не соседняя; почему ошибки возвращаются, а не бросаются; почему миграции только
вперёд. Не записываются команды проверок (они в конфиге) и пересказ структуры кода.
Отменённое решение удаляется из файла, а не копится с пометкой «устарело».
Пайплайн не настроен (нет `.pipeline/config.yml`) — остановитесь и предложите `/pipeline:init`.

## Шаг 2. Ветка

Прежде чем ответвляться, проверьте расхождение локального `main` с `origin/main` — в обе
стороны:

    git switch main
    git fetch origin main
    git status

`git status` после `fetch` (не после `pull`) прямо называет расхождение: «behind» — локальный
`main` отстал от `origin/main`, «ahead» — обогнал его, «diverged... N and M different commits
each» — разошлись сразу в обе стороны. Одного `git pull` для этой проверки недостаточно: если
`main` обогнал `origin/main`, `pull` молча завершится как «Already up to date» и ничего не
покажет, а ветка ответвится от состояния, которого нет на сервере, — PR получится не с тем
содержимым, которое ожидалось.

- **Отстал** — обычный случай, `git pull` (fast-forward) закроет расхождение.
- **Обогнал** — на локальном `main` есть коммиты, которых нет на GitHub (типичная причина:
  в прошлый раз закоммитили и забыли запушить). Разберитесь, откуда они, и запушите их
  (`git push origin main`) до создания ветки — иначе они попадут в диф вашего PR вперемешку
  с текущим изменением.
- **Разошлись в обе стороны** — остановитесь и разберитесь вручную, кто и что закоммитил;
  не мёржите и не ребейзьте `main` автоматически.

Только когда `main` синхронизирован (или расхождение осознанно устранено), создавайте ветку:

    git switch -c feat/<короткое-имя-задачи>

## Шаг 3. Сначала тест, если проект вышел из наброска

При `stage: sketch` можно писать код сразу — на этой стадии тесты мешают искать форму решения.

Начиная со `stage: shaping` сначала пишется тест на желаемое поведение, и он должен
покраснеть до того, как появится реализация. Тест, который не падал ни разу, ничего не
доказывает: в этом проекте уже отгружались тесты, проходившие при любой реализации.

Тест описывает поведение, а не устройство: он должен пережить переписывание внутренностей.

## Шаг 4. Локальные проверки до пуша

    sh scripts/pipeline.sh all

Гонять до зелёного здесь, а не в CI. Каждый круг «push → ждать CI → красный» стоит минут,
локальный прогон — секунд.

Если менялся `.pipeline/config.yml`, перегенерируйте артефакты, иначе `drift-check` покраснеет:

    node ${CLAUDE_PLUGIN_ROOT}/src/cli.mjs generate .

## Шаг 5. Зафиксировать изменения

    git add <изменённые файлы>
    git commit -m "<тип>: <описание>"

Без коммита пушить нечего: `git push` без единого нового коммита в ветке отправит на GitHub то
же самое, что уже есть в `main`, и PR окажется пустым. Сообщение коммита — на русском языке,
в формате `<тип>: <описание>` (`feat`, `fix`, `docs`, `test`, `refactor` — по характеру
изменения), без подписи соавтора. Если изменение состоит из нескольких осмысленных частей —
разбейте на несколько коммитов, а не сваливайте всё в один.

## Шаг 6. PR

    git push -u origin feat/<имя>
    gh pr create --title "<что сделано>" --body "<что сделано; что проверено и как>"

В теле PR — что изменилось и какими командами это проверено. Не пересказ диффа: его видно.

## Шаг 7. Зелёный CI

    gh pr checks --watch

Красный — передайте работу скиллу `pipeline-ci-doctor`. Он возьмёт диагноз по логу, починит
причину и ограничит число попыток тремя. Не чините вслепую сами и не считайте попытки в уме.

## Шаг 8. Мердж по режиму автономности

Поле `autonomy` в конфиге определяет, кто принимает решение:

- `full` — мерджить самостоятельно: `gh pr merge --auto --squash --delete-branch`;
- `merge-gate` — остановиться. Сообщить человеку, что PR зелёный и ждёт его решения. Не мерджить;
- `prod-gate` — смерджить самостоятельно: `gh pr merge --auto --squash --delete-branch`, но деплой не запускать.

Про `prod-gate` важно: деплой пока не реализован — он появится в отдельном плане. Смерджив PR
в этом режиме, скажите прямо, что изменения в `main`, но никуда не выкачены. Не создавайте
впечатление, будто что-то развёрнуто.

## Критерий завершения

Задача завершена, когда PR смерджен (`full`, `prod-gate`) либо когда он зелёный и человек
уведомлён (`merge-gate`). Зелёные локальные проверки при красном или неизвестном CI —
не завершение.
