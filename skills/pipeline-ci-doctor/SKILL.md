# Починка красного CI

Задача — не «сделать джобу зелёной», а понять, что именно сломалось, и починить причину.
Замена проверки на более слабую, отключение теста и правка порога, чтобы «прошло», —
это не починка, а сокрытие: следующий раз то же самое сломается в проде.

## Шаг 0. Проверить счётчик попыток — прежде чем что-либо делать

Лимит — три попытки на PR, и его нельзя определить на глаз или по памяти: сессия могла
прерваться и начаться заново. Единственный источник правды, переживающий такой перезапуск, —
комментарии к PR. Поэтому это первый шаг, раньше, чем диагноз или код.

1. Получить номер PR и текущий SHA его ветки на GitHub. Именно на GitHub, а не локальным
   `git rev-parse HEAD`: если локальная копия отстала от того, что реально запушено, он соврёт.

       PR=$(gh pr view --json number --jq .number)
       SHA=$(gh pr view --json headRefOid --jq .headRefOid)

   Дальше по всему скиллу вместо номера PR используется именно `$PR`. `gh pr view`,
   `gh pr comment` и `gh pr checks` умеют сами подставлять PR текущей ветки, если номер не
   передан явно — но здесь он явно сохранён в переменную, чтобы каждый следующий шаг
   подставлял одно и то же значение, а не запрашивал его заново.

2. Выгрузить тела всех комментариев к PR и найти среди них две фиксированные формы записи
   (их пишет этот же скилл — формат записи в шаге 4 и формат чтения здесь совпадают
   намеренно, иначе прочитанное не совпадёт с написанным):

       gh pr view "$PR" --json comments --jq '.comments[].body' > /tmp/pr-comments.txt
       grep -E '^Пайплайн-доктор: старт, базовый коммит [0-9a-f]+' /tmp/pr-comments.txt
       grep -E '^Попытка [0-9]+ \(commit [0-9a-f]+\):' /tmp/pr-comments.txt

3. Ничего не нашлось (ни строки «старт», ни строки «Попытка») — это первое обращение к
   этому PR. До того как читать диагноз, зафиксируйте точку отсчёта:

       gh pr comment "$PR" --body "Пайплайн-доктор: старт, базовый коммит $SHA"

   Потрачено попыток: N = 0. Идите к шагу 1 — попытка, которую вы сейчас начинаете, первая.

4. Нашлась хотя бы одна строка — разберите строки «Попытка»: число сразу после слова
   «Попытка» — номер попытки, значение в скобках после `commit` — её SHA. Если такая строка
   не одна, возьмите ту, где номер максимален (независимо от порядка, в котором GitHub
   вернул комментарии) — практически это делает одна команда:

       LAST=$(grep -E '^Попытка [0-9]+ \(commit [0-9a-f]+\):' /tmp/pr-comments.txt | sort -t' ' -k2 -n | tail -1)

   Если `$LAST` не пустая строка: N — это число из неё (`sed -E 's/^Попытка ([0-9]+).*/\1/'`),
   LAST_SHA — это SHA из неё (`sed -E 's/.*\(commit ([0-9a-f]+)\).*/\1/'`).
   Если строк «Попытка» нет, а есть только строка «старт»: N = 0, а LAST_SHA — SHA из
   строки «старт».

5. Сравните `$SHA` с `LAST_SHA` — это и есть проверка на потерянную попытку:
   - Совпадают — с прошлого раза никто не пушил. Потрачено ровно N попыток.
   - Не совпадают — кто-то запушил коммит после последней зафиксированной точки и не
     отчитался: либо предыдущая сессия оборвалась после push, но до комментария, либо она
     ещё работает параллельно. Чтобы счёт не занижался, эта попытка тоже считается потраченной,
     даже без подробностей о ней. Немедленно восстановите журнал и увеличьте счёт:

           gh pr comment "$PR" --body "Попытка $((N + 1)) (commit $SHA): комментарий не был оставлен предыдущей сессией — восстановлено автоматически, подробности попытки неизвестны"

     Дальше N = N + 1.

6. N ≥ 3 — остановитесь прямо здесь. Не запускайте диагностику, не открывайте лог, не
   трогайте код. В ответе человеку сошлитесь на комментарии к PR как на журнал: три попытки
   уже потрачены, дальше нужно его решение. Это нормальный итог шага 0, а не пропущенная работа.

7. N < 3 — переходите к шагу 1. Попытка, которую вы сейчас начинаете, имеет номер N + 1 —
   это число понадобится в шаге 4, когда придёт время отчитаться о её результате.

## Шаг 1. Взять диагноз, а не сырой лог

Номер PR уже известен из шага 0 (`$PR`). Получить id упавшего прогона — тоже командой, а не
угадывая: это самый свежий прогон на текущей ветке с `conclusion == "failure"`.

    RUN=$(gh run list --branch "$(git branch --show-current)" --limit 10 --json databaseId,conclusion --jq '[.[] | select(.conclusion=="failure")][0].databaseId')
    gh run view "$RUN" --log-failed > /tmp/failed.log

Получить диагноз:

    node ${CLAUDE_PLUGIN_ROOT}/src/cli.mjs diagnose . /tmp/failed.log

Он покажет упавшую джобу, шаг, сообщения об ошибках и последние строки вывода — без
временных меток, ANSI-кодов и эха команд. Если шаг соответствует проверке из
`.pipeline/config.yml`, диагноз назовёт её команду и скажет, обязательная ли она.

Читать весь сырой лог не нужно. Открывайте его, только если диагноза не хватило —
и тогда скажите об этом в отчёте: значит, разбор чего-то не понимает.

## Шаг 2. Отделить поломку кода от поломки пайплайна

Красная джоба `drift-check` означает не ошибку в коде, а рассогласование: `.pipeline/config.yml`
изменили, а артефакты не перегенерировали. Чинится одной командой:

    node ${CLAUDE_PLUGIN_ROOT}/src/cli.mjs generate .

После неё `.github/workflows/ci.yml` и `scripts/pipeline.sh` нужно закоммитить вместе с конфигом.

Красная джоба `checks` означает, что упала конкретная проверка проекта. Её команду диагноз
уже назвал — воспроизведите падение локально той же командой, прежде чем что-то править.
Правка вслепую по тексту ошибки из CI — самый частый способ потратить попытку впустую.

## Шаг 3. Починить причину

Воспроизвели локально — чините. Проверка проходит локально — коммит и push в ту же ветку.

Если падение не воспроизводится локально, причина в различии окружений: версия Node, регистр
имён файлов, переводы строк, отсутствующая переменная окружения, порядок тестов. Ищите различие,
а не подгоняйте код.

## Шаг 4. Зафиксировать попытку

Каждая попытка — это push с исправлением и ожидание результата:

    gh pr checks --watch

После результата — независимо от того, помогло исправление или нет, — оставьте комментарий
к PR строго в том формате, что шаг 0 умеет разбирать (иначе следующая сессия его не найдёт
и занизит счёт). Номер попытки — это N + 1 из шага 0; коммит — тот, что только что запушен:

    SHA=$(git rev-parse HEAD)
    gh pr comment "$PR" --body "Попытка N (commit $SHA): <что было сломано> → <что изменено> → <результат>"

где `N` нужно заменить на настоящий номер попытки (N + 1 из шага 0) — это единственное, что
здесь не подставляется автоматически. Часть `(commit $SHA)` менять не нужно: именно по ней
шаг 0 в следующий раз опознает, что за коммит был запушен в этой попытке.

CI всё ещё красный, а лимит не исчерпан — возвращайтесь к шагу 1: диагноз мог измениться
после изменений. CI зелёный — задача решена. Если только что записанная попытка была
третьей, а CI всё ещё красный — остановитесь и отчитайтесь человеку: что падало, что
пробовали, почему не сработало, какая гипотеза осталась непроверенной. Это нормальный исход,
а не провал. Продолжать вслепую четвёртый раз — значит жечь время и бюджет.

## Чего не делать

- Не отключайте и не ослабляйте упавшую проверку, чтобы получить зелёный.
- Не убирайте проверку из `required` в конфиге ради прохождения PR.
- Не пушьте с `--force` в ветку PR.
- Не объявляйте починку успешной, не дождавшись зелёного: `gh pr checks --watch`.
