# Agent Pipeline — спецификация

Дата: 2026-08-22
Статус: утверждён к реализации

## 1. Задача

Формализовать повторяющийся способ работы: человек пишет промпт, агент правит код, гоняет
проверки, пушит, открывает PR, дожидается CI, чинит красное, мерджит и выкатывает. Сейчас это
воспроизводится вручную в каждом новом проекте. Нужен переиспользуемый каркас, который
разворачивается в новый или существующий проект и растёт вместе с ним.

Каркас должен быть пригоден для передачи другим людям, не только для личного использования.

## 2. Ключевые решения

| Решение | Выбор | Причина |
|---|---|---|
| Форма поставки | Гибрид: плагин + шаблоны в одном репо | Обновляемая логика при прозрачном и самодостаточном проекте |
| Автономность | Параметр проекта (`full` / `merge-gate` / `prod-gate`) | Пет-проект и боевой сервис требуют разного |
| Агент в CI | Нет, только локальный | Ноль ключей в облаке, ноль дополнительного биллинга |
| Стеки v1 | node-ts, python, go, java | То, на чём пишет владелец |
| Деплой v1 | Docker на собственный VPS | Единственный реально используемый сценарий |
| Взросление | Органическое, по наблюдаемым сигналам | Ручной флаг уровня — бюрократия, от которой уходим |
| Применение ужесточений | Отдельный PR «взросление» | Правила игры не меняются без ведома человека |

## 3. Архитектура

Одно публичное репо `agent-pipeline` служит одновременно marketplace для плагина и хранилищем
шаблонов.

```
agent-pipeline/
├─ .claude-plugin/
│  ├─ marketplace.json          источник "./" — репо ставится одной командой
│  └─ plugin.json
├─ skills/                      МОЗГИ: обновляются централизованно
│  ├─ pipeline-init/            развернуть каркас в проект
│  ├─ pipeline-ship/            промпт → код → тесты → PR → merge → deploy
│  ├─ pipeline-ci-doctor/       красная джоба → диагноз → фикс → push
│  ├─ pipeline-evolve/          переход между стадиями зрелости
│  └─ pipeline-deploy/          выкатка, healthcheck, откат
├─ commands/                    /pipeline:init, /pipeline:ship, /pipeline:fix-ci,
│                               /pipeline:evolve, /pipeline:reconfigure
├─ hooks/
│  ├─ hooks.json                SessionStart + PreToolUse
│  └─ run-hook.cmd              кроссплатформенный запуск (владелец на Windows)
├─ templates/                   КОСТИ: копируются в проект и коммитятся там
│  ├─ common/                   .pipeline/, .github/workflows/, .claude/settings.json
│  ├─ stacks/{node-ts,python,go,java}/   Dockerfile, пресет проверок, smoke-тест
│  └─ deploy/docker-vps/        compose.yml, deploy.sh, rollback.sh
├─ tests/                       тесты самого шаблона (см. §10)
└─ README.md
```

### Граница мозгов и костей

Мозги знают, **как рассуждать**. Кости знают, **что именно запускать в этом проекте**.

Инвариант: всё необходимое для зелёного CI и деплоя лежит в репозитории проекта и коммитится.
Плагин можно удалить — проект продолжит собираться, тестироваться и выкатываться. Агент является
ускорителем, а не рантайм-зависимостью. Это же условие делает проект пригодным для передачи:
человек клонирует репо и всё работает, плагин ставит только если хочет агентную часть.

## 4. Контракт: `.pipeline/config.yml`

Единственный источник правды о проекте. Заполняется агентом в ходе init, правится агентом по
команде `/pipeline:reconfigure`. Ручная правка допустима, но не является основным путём.

```yaml
version: 1
project:
  name: my-app
  stack: node-ts              # node-ts | python | go | java
  goal: "короткое описание цели, записывается со слов человека при init"
autonomy: prod-gate           # full | merge-gate | prod-gate
stage: sketch                 # sketch | shaping | product | sustained
checks:                       # реальные команды, снятые с проекта, а не угаданные
  test: npm run test -- --run
  lint: npm run lint
  typecheck: npx tsc --noEmit
  build: npm run build
required: [build]             # что валит CI на текущей стадии
deploy:
  target: docker-vps
  registry: ghcr.io/<owner>/my-app
  environments:
    staging:    { host: staging.example.com, auto: true }
    production: { host: example.com, auto: false }
  healthcheck: { path: /healthz, timeout_sec: 60 }
  backup_before_migrate: false
  secrets: [SSH_KEY, REGISTRY_TOKEN]   # имена, не значения
```

Файл коммитится, поэтому в нём не должно быть ни ключей, ни паролей — только адреса и **имена**
секретов. Значения живут в GitHub Secrets.

### Генерация вместо рантайм-парсинга

`.github/workflows/ci.yml`, `.github/workflows/deploy.yml` и `scripts/pipeline.sh` **генерируются**
из конфига при `init` и `evolve`: команды подставляются плоско, парсинг YAML в рантайме не
требуется, лишних зависимостей в CI нет.

Чтобы генерируемые файлы не разъехались с конфигом, в CI работает джоба `drift-check`: она
перегенерирует артефакты и сравнивает с закоммиченными. Расхождение — красный, по принципу
`terraform plan`.

`scripts/pipeline.sh` даёт человеку локально ровно те же команды, что гоняет CI. На Windows
запускается через Git Bash, в CI — на `ubuntu-latest`.

## 5. Bootstrap и init

### Два входа

| Вход | Сценарий | Действие |
|---|---|---|
| Плагин | есть существующий проект | `/pipeline:init` в папке проекта |
| Шаблон (fork / zip / degit) | новый проект или переданный шаблон | распаковать → `claude` → агент заводит разговор сам |

Второй вход держится на SessionStart-хуке в `.claude/settings.json` шаблона: хук проверяет наличие
`.pipeline/config.yml` и, если файла нет, подмешивает в старт сессии сообщение о том, что пайплайн
не настроен и следует предложить `/pipeline:init`. Человеку не нужно знать ни одной команды.

### Init — расследование, затем интервью

Порядок принципиален: агент сначала узнаёт всё, что может узнать сам, и спрашивает только остаток.

Определяет молча:

- стек — по `package.json` / `pyproject.toml` / `go.mod` / `pom.xml` / `build.gradle`;
- реальные команды проверок — из скриптов проекта, а не по шаблону;
- состояние репозитория — `gh repo view`: наличие remote, default-ветка, включены ли Actions;
- контейнеризацию — наличие `Dockerfile` и compose-файла;
- работоспособность тестов — пробным прогоном.

Спрашивает у человека:

- цель проекта и критерий успеха;
- режим автономности;
- хост и registry, что считается продом;
- нужен ли бэкап перед миграциями.

Если удалённого репозитория ещё нет, init предлагает создать его через `gh repo create` и
спрашивает про приватность. Без remote проверить пайплайн на настоящем CI невозможно, поэтому шаг
обязателен — но создание репозитория выполняется только с явного согласия человека.

### Проверка окружения до генерации

Три проверки, каждая из которых иначе проявляется в середине процесса и выглядит как отказ на
ровном месте. Обе первые встретились при разработке самой спецификации, поэтому включены не
умозрительно.

**Атрибуция коммитов.** `git config user.email` может указывать на личность, не привязанную к
рабочему GitHub-аккаунту: глобальный config, унаследованный от другого проекта, или адрес,
привязанный к постороннему аккаунту. Коммиты при этом создаются успешно, но на GitHub числятся за
чужим профилем. Проверка после первого коммита:

```
gh api repos/<owner>/<repo>/commits --jq '.[0].author.login'
```

Пусто или не совпадает с владельцем — предложить `git config --local` с noreply-адресом вида
`<id>+<login>@users.noreply.github.com`, где id берётся из `gh api user`.

**Scope `workflow` у токена.** Без него `gh` создаёт репозиторий и пушит обычные файлы нормально, а
первый же пуш `.github/workflows/` отклоняется. Проверяется через `gh auth status` до генерации
workflow, а не после.

**Включены ли Actions** в репозитории — иначе PR будет вечно ждать проверок, которые никто не
запустит.

### Критерий завершения init

Init считается завершённым не когда файлы записаны, а когда **зелено**:

1. `scripts/pipeline.sh` отработал локально на всех объявленных проверках;
2. открыт PR, содержащий сам пайплайн;
3. CI на этом PR зелёный.

Это защита от основного режима отказа: агент записывает в конфиг команду, которой в проекте нет.
Пайплайн доказывает себя на себе же, первым PR.

Для пустого проекта тестов ещё нет — init создаёт минимальный скелет и один smoke-тест, чтобы CI
был зелёным с первого дня, до появления первой фичи.

Уточнение про стадию `sketch`: она разрешает push прямо в main, но сам init всё равно проходит
через PR. Причина в том, что PR здесь не процедура согласования, а единственный способ увидеть
пайплайн работающим на настоящем CI до того, как на него положатся. После завершения init на
стадии `sketch` человек снова волен пушить в main напрямую.

### Где сказано, что настройкой занимается агент

Три места, по убыванию навязчивости: SessionStart-хук (сам, в нужный момент), шапка
`.pipeline/config.yml`, раздел README «Настройка».

## 6. Взросление проекта

Ручной флаг уровня зрелости не используется. Стадия — следствие наблюдаемого состояния проекта.

### Стадии

| Стадия | Состояние | Что делает CI |
|---|---|---|
| `sketch` | быстрый промптинг, обрисовка идеи | только «стартует ли» — build / import smoke. Ни линта, ни тестов. Push в main разрешён |
| `shaping` | накопились зависимости, появилась структура | агент пишет тесты на желаемое поведение, а не на реализацию. PR-флоу обязателен. Линт предупреждает, но не валит |
| `product` | есть прод и пользователи | тесты обязательны, типы строгие, аудит зависимостей, бэкап перед миграцией, откат по healthcheck |
| `sustained` | живёт долго, не только владелец | матрица версий, порог покрытия, релизные теги, changelog, security scan |

### Триггеры перехода

Сигналы размера (считаются автоматически):

- `sketch → shaping`: ≥15 файлов исходников ИЛИ ≥8 прямых зависимостей ИЛИ ≥30 коммитов;
- `shaping → product`: настроен деплой в окружение `production` ИЛИ ≥60 файлов ИЛИ ≥5000 строк;
- `product → sustained`: ≥2 контрибьютора ИЛИ ≥6 месяцев с первого коммита ИЛИ был хотфикс мимо PR.

Сигналы боли — точнее любого счётчика строк:

- откат прода → повышение стадии на одну (проверок оказалось недостаточно);
- второй баг того же класса в одном модуле → предложение тест-барьера именно туда, без смены стадии;
- main красный дольше 24 часов → предложение по процессу, а не по коду.

### Наблюдаемость

`.pipeline/state.json` хранит снимок метрик и текущую стадию. Обновляется SessionStart-хуком и
шагом в CI. Когда порог перейдён, агент видит это в начале сессии как факт, а не вспоминает.
Дополнительно джоба в CI открывает issue при переходе порога — сигнал доходит, даже если проект не
открывали месяцами.

### Реакция на переход

Агент не трогает текущую задачу. Он сообщает, что проект перерос стадию, показывает, что предлагает
ужесточить и что при этом сломается, и открывает **отдельный PR «взросление»**. Решение за
человеком.

### Храповик

Основная причина провала ужесточений: включили строгие правила, получили сотни ошибок, выключили
обратно. Поэтому новые правила применяются только к изменённому коду, а состояние существующего
фиксируется в `.pipeline/baseline.json`, который может только уменьшаться.

Реализация по стекам:

- node-ts — eslint по списку из `git diff --name-only`, строгий tsconfig с явным списком файлов,
  порог покрытия «не ниже зафиксированного»;
- python — `ruff` по диффу, baseline для `mypy`;
- go — `golangci-lint --new-from-rev=origin/main`;
- java — checkstyle/spotless по изменённым файлам.

Строгость растёт монотонно, но CI не краснеет одномоментно.

### Соглашения

`.pipeline/conventions.md` — решения, принятые по ходу проекта («тесты на vitest, не jest», «ошибки
возвращаем, не бросаем», «миграции только вперёд»). Агент дописывает файл при принятии решения и
читает при каждой итерации. Это память между сессиями: без файла соглашения держатся на длине
контекста и рассыпаются через несколько недель.

## 7. Цикл итерации

`/pipeline:ship <задача>`:

1. читает `config.yml`, `conventions.md`, `state.json`;
2. создаёт ветку `feat/<slug>` от main;
3. со стадии `shaping` — сначала тест на желаемое поведение (переиспользует навык TDD);
4. правит код, гоняет локальные проверки до зелёного;
5. коммит, push, `gh pr create` с телом: что сделано, что проверено;
6. `gh pr checks --watch`;
7. при красном — `pipeline-ci-doctor`: `gh run view --log-failed` → диагноз → фикс → push.
   **Лимит 3 попытки**, затем отчёт человеку: что пробовал и почему не вышло. Без лимита агент
   уходит в цикл «фикс → красный → фикс»;
8. при зелёном — по `autonomy`:
   - `full` → `gh pr merge --auto --squash`,
   - `merge-gate` → остановка, ход человека,
   - `prod-gate` → merge и автоматический деплой на staging;
9. деплой (см. §8).

## 8. Деплой и откат

Сценарий `docker-vps`:

1. сборка образа, тег равен commit SHA;
2. push в registry;
3. SSH на целевой хост, `docker compose up -d`;
4. healthcheck по адресу и таймауту из конфига;
5. healthcheck не прошёл → откат на предыдущий известный зелёный тег → открытие issue с логами.

Тег как commit SHA выбран сознательно: на откате хитрая схема версионирования только мешает.

Со стадии `product`, если включён `backup_before_migrate`: дамп БД сохраняется в артефакт до
применения миграций, откат восстанавливает его. Откат кода при уже применённой миграции ломает прод
сильнее, чем исходный неудачный деплой.

Продакшн-окружение с `auto: false` защищено GitHub Environments с ручным approve.

## 9. Безопасность

Хуки плагина:

- `PreToolUse` на `git push` в main начиная со стадии `shaping` — блокировка с указанием создать ветку;
- отказ коммитить содержимое, похожее на секрет (проверка по типовым паттернам ключей и токенов);
- запрет `git push --force` в main.

Правило для передачи шаблона другим людям: SessionStart-хук в шаблоне **печатает текст и только
текст** — ни сетевых вызовов, ни записи на диск, ни установки зависимостей. Человек, скачавший
шаблон, исполняет этот хук автоматически при первом запуске, поэтому хук обязан быть безобидным
настолько, чтобы его не требовалось аудировать. Всё, что вносит изменения, живёт в скиллах и
запускается агентом на глазах у пользователя.

## 10. Тестирование шаблона

Для каждого из четырёх стеков CI репозитория `agent-pipeline`:

1. создаёт пустой проект во временной папке;
2. прогоняет init в неинтерактивном режиме с фикстурой ответов;
3. проверяет, что объявленные проверки проходят;
4. валидирует сгенерированный workflow через `actionlint`;
5. проверяет `drift-check`: повторная генерация не даёт расхождений.

Репозиторий шаблона живёт по своему же пайплайну (догфудинг): поломка обнаруживается раньше, чем
её увидят пользователи.

## 11. Вне области первой версии

Исключено сознательно, добавляется при появлении реальной потребности:

- PaaS-деплой (Vercel, Railway, Fly) и Kubernetes;
- агент, работающий внутри GitHub Actions;
- монорепо с несколькими языками одновременно;
- форджи кроме GitHub.

## 12. Критерии готовности первой версии

- плагин ставится с GitHub одной командой, скиллы и команды видны в сессии;
- `/pipeline:init` на пустой папке для стека node-ts даёт зелёный CI за один проход;
- `/pipeline:init` на существующем python-проекте не ломает его существующие тесты;
- `/pipeline:ship` доводит тривиальную задачу от промпта до мерджа без ручного вмешательства;
- деплой на реальный VPS работает, а искусственно сломанный healthcheck приводит к откату;
- тесты шаблона (§10) зелёные для всех четырёх стеков.
